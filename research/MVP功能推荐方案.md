# MVP 功能推荐方案

> 项目：KaiLionCrafts 外贸获客 AI 工作台 V77.3.2
> 基于：现有工作台基线 + 21个GitHub开源项目 + 17个商业产品 + 14个视频/方法论 + 30项差距矩阵
> 报告日期：2026-10-03
> 原则：真实外贸B2B业务价值优先，不堆功能，不引入付费API，不破坏现有37功能

## 一、候选功能详细评估

### 候选1：线索质量和邮箱质量评分

| 评估项 | 内容 |
|--------|------|
| **用户问题** | 导入或搜索到的线索质量参差不齐，无效邮箱导致退信损害域名声誉，低质量客户浪费开发精力。无法在开发前判断"这个客户值不值得花时间写开发信"。 |
| **业务价值** | 🔴高——聚焦高价值客户，减少无效开发，保护发件域名声誉。退信率从不可控变为可监控。 |
| **使用流程** | 1.客户导入/搜客后自动运行评分 → 2.显示邮箱质量(✅有效格式/⚠️可疑/❌无效)和线索质量分(0-100) → 3.低质量线索标记"建议先补充资料" → 4.高质量线索优先进入outreachQueue |
| **输入数据** | 客户对象(company/website/email/country/customerType)、website-evidence证据(reviewStatus/fetchedAt/contentHash)、DNC状态、duplicate状态、Knowledge Pack绑定状态 |
| **输出数据** | emailQuality{type(企业/个人/免费邮箱), domainQuality, formatValid, mxChecked(可选), confidenceScore}、leadQualityScore(0-100)、leadQualityTier(A/B/C/D)、qualityBreakdown、qualityWarnings[] |
| **所需接口** | 新增前端函数calculateLeadQuality()、calculateEmailQuality()；可复用prospect-priority.js的评分框架 |
| **是否需要模型** | ❌不需要——纯规则评分(邮箱格式正则、域名MX记录DNS查询可选、网站有效性HTTP检查、证据新鲜度计算) |
| **是否需要外部API** | ❌不需要付费API——MX记录可用Node.js dns模块免费查询，网站有效性用现有website-evidence.js抓取 |
| **是否涉及客户隐私** | 🟡低——仅处理客户公开联系方式，不涉及敏感数据 |
| **开发成本** | 🟡中——约400-600行代码，新增2个评分函数+UI展示+数据字段 |
| **测试成本** | 🟢低——规则评分可单元测试，覆盖邮箱格式/域名/证据/DNC等场景 |
| **维护成本** | 🟢低——规则稳定，无需频繁更新 |
| **失败处理** | DNS查询超时→标记"待确认"不降级；网站抓取失败→不扣分仅标记"未验证"；评分函数异常→返回默认分50并记录warning |
| **推荐等级** | ⭐⭐⭐⭐⭐ P1——MVP必选 |

**评分维度设计**：
- 邮箱质量(40分)：格式有效(10)+企业域名非免费邮箱(10)+MX记录存在(10)+域名与公司名匹配(10)
- 网站质量(20分)：有官网(10)+官网可访问(5)+有reviewed证据(5)
- 证据新鲜度(15分)：证据<30天(15)+30-90天(10)+>90天(5)+无证据(0)
- 联系完整度(15分)：有联系人(5)+有邮箱(5)+有国家(5)
- ICP匹配(10分)：复用prospect-priority的ICP匹配结果

### 候选2：多联系人决策链

| 评估项 | 内容 |
|--------|------|
| **用户问题** | B2B采购涉及3-5决策人(Buyer/Owner/Procurement/Product Manager/Import Manager)，当前单联系人结构无法管理。开发信发给了错误的人，或只联系了一个人就放弃。 |
| **业务价值** | 🟠中高——提高触达正确决策人的概率，但单人业务中客户量不大时优先级可延后。 |
| **使用流程** | 1.客户详情页新增"联系人"列表 → 2.添加联系人(姓名/职位/邮箱/电话/LinkedIn/角色标签) → 3.标记主要联系人/Champion → 4.开发信可选择发给哪个联系人 → 5.跟进记录关联到具体联系人 |
| **输入数据** | 客户ID、联系人信息(姓名/职位/邮箱/电话/LinkedIn/角色/影响力/是否Champion) |
| **输出数据** | contacts[]数组、primaryContactId、championContactId、decisionChainSummary |
| **所需接口** | 数据模型变更(customer.contact → customer.contacts[])、新增CRUD函数、UI联系人管理组件、开发信收件人选择 |
| **是否需要模型** | ❌不需要——纯数据管理 |
| **是否需要外部API** | ❌不需要 |
| **是否涉及客户隐私** | 🟡中——存储多个联系人的个人信息，需确保本地存储安全 |
| **开发成本** | 🔴高——数据模型变更影响客户台账/开发信/跟进/导入导出等多个模块，约800-1200行代码 |
| **测试成本** | 🟡中——需回归测试所有涉及客户数据的功能 |
| **维护成本** | 🟡中——联系人数据需人工维护 |
| **失败处理** | 兼容旧数据(contact单对象自动迁移为contacts[0])、联系人删除时检查关联的开发信/跟进记录 |
| **推荐等级** | ⭐⭐⭐ P2——MVP后第二阶段，客户量增长后必需 |

### 候选3：购买信号和客户事件时间线

| 评估项 | 内容 |
|--------|------|
| **用户问题** | 无法主动捕捉客户的采购时机(招聘采购经理/融资/展会/新产品/官网改版)，总是被动等待客户回复。研究显示35-50%单子给第一个响应者。 |
| **业务价值** | 🟠中高——从被动开发变为主动触发，但需要外部数据源和定时任务。 |
| **使用流程** | 1.对A级客户启用信号监控 → 2.定期(每周)检查官网变化(contentHash对比)+招聘页面+新闻 → 3.检测到变化时生成事件记录 → 4.事件时间线展示 → 5.推荐对应开发信钩子 |
| **输入数据** | 客户官网URL、已有evidence的contentHash、客户公司名 |
| **输出数据** | buyingSignals[{type, date, source, description, confidence, recommendedHook}]、eventTimeline[]、signalAlertCount |
| **所需接口** | 定时任务(需server.js新增cron或手动触发)、官网重采(复用website-evidence.js)、contentHash对比、新闻搜索(需Tavily或类似，当前未配置) |
| **是否需要模型** | 🟡可选——AI可辅助判断信号相关性，但规则匹配即可 |
| **是否需要外部API** | 🟡部分需要——官网重采不需要，但新闻/招聘搜索需要Tavily(免费1000次/月)或类似 |
| **是否涉及客户隐私** | 🟢低——仅处理公开信息 |
| **开发成本** | 🔴高——需要定时任务框架、信号检测逻辑、时间线UI、事件-开发信关联，约800-1000行 |
| **测试成本** | 🟡中——需模拟信号检测、时间线渲染、告警逻辑 |
| **维护成本** | 🟡中——信号源可能变化，检测规则需更新 |
| **失败处理** | 定时任务失败→记录日志下次重试；外部API不可用→降级为仅官网变化检测；信号误报→人工可标记"忽略" |
| **推荐等级** | ⭐⭐⭐ P2——MVP后第二阶段，需先配置Tavily搜索 |

### 候选4：客户开发任务队列增强

| 评估项 | 内容 |
|--------|------|
| **用户问题** | Campaign Task失败后无自动重试，任务可能静默丢失。无预计耗时、无任务历史、无失败原因分类。单人外贸最大的问题是跟进不及时导致客户流失。 |
| **业务价值** | 🔴高——确保每个客户开发任务都有始有终，不遗漏，提高执行效率。直接复用现有Campaign Task基础设施。 |
| **使用流程** | 1.dailyWork页面显示今日任务队列(按优先级排序) → 2.每个任务显示状态/预计耗时/失败原因 → 3.失败任务可一键重试 → 4.任务完成自动记录历史 → 5.逾期任务标红预警 |
| **输入数据** | Campaign Task(现有)、客户优先级评分、任务类型(research/evidence/draft/review/followup) |
| **输出数据** | taskQueue[{taskId, customerId, taskType, priority, status, estimatedMinutes, failureReason, retryCount, lastAttemptAt, nextRetryAt}]、taskHistory[]、overdueTaskCount |
| **所需接口** | 扩展Campaign Task数据结构(新增failureReason/retryCount/estimatedMinutes/nextRetryAt)、新增retryCampaignTask()、任务队列排序函数、dailyWork UI增强 |
| **是否需要模型** | ❌不需要——纯任务管理 |
| **是否需要外部API** | ❌不需要 |
| **是否涉及客户隐私** | 🟢低——任务元数据 |
| **开发成本** | 🟡中——约400-600行，扩展现有结构而非新建 |
| **测试成本** | 🟢低——复用现有Campaign Task测试，新增重试/逾期场景 |
| **维护成本** | 🟢低——任务逻辑稳定 |
| **失败处理** | 重试上限(3次)后标记"需人工介入"；重试间隔递增(1min/5min/15min)；任务异常不影响其他任务 |
| **推荐等级** | ⭐⭐⭐⭐⭐ P1——MVP必选 |

### 候选5：开发信质量检查

| 评估项 | 内容 |
|--------|------|
| **用户问题** | AI生成的开发信可能包含未确认事实、敏感信息、缺少CTA、过长、垃圾邮件风险词、未引用真实证据。当前完全依赖人工审核发现，审核负担重，遗漏风险高。 |
| **业务价值** | 🔴高——在人工审核前自动过滤明显问题，提高审核效率，保护域名声誉，确保所有事实有来源。这是工作台"证据驱动"理念的自然延伸。 |
| **使用流程** | 1.AI生成草稿后自动运行质量检查 → 2.显示质量分(0-100)+问题清单(按严重程度排序) → 3.点击问题定位到草稿对应位置 → 4.修复后重新检查 → 5.质量分达标(≥70)才能进入reviewQueue |
| **输入数据** | 草稿文本、关联客户的evidence列表(reviewed+publicUseAllowed)、Knowledge Fact列表(confirmed+publicUseAllowed)、客户信息、sanitizeFactsForAI规则 |
| **输出数据** | draftQualityScore(0-100)、qualityIssues[{severity(critical/warning/info), category, message, location, suggestion}]、qualityChecks[{name, passed, detail}] |
| **所需接口** | 新增checkDraftQuality()函数(纯规则)、草稿UI新增质量面板、reviewQueue新增质量分筛选、质量门控(低分阻止提交审核) |
| **是否需要模型** | ❌不需要——纯规则检查(正则+关键词+证据匹配+长度计算)。AI可辅助但规则更可靠可控 |
| **是否需要外部API** | ❌不需要——所有检查基于本地数据 |
| **是否涉及客户隐私** | 🟢低——检查草稿文本，不新增数据 |
| **开发成本** | 🟡中——约500-700行，规则引擎+UI面板+门控逻辑 |
| **测试成本** | 🟢低——可构造各种问题草稿做单元测试(未确认事实/敏感词/缺CTA/过长/无证据等) |
| **维护成本** | 🟢低——规则稳定，垃圾邮件关键词库可定期更新 |
| **失败处理** | 检查函数异常→不阻止草稿提交，显示"质量检查暂不可用"warning；证据数据缺失→对应检查项标记"无法验证"而非失败 |
| **推荐等级** | ⭐⭐⭐⭐⭐ P1——MVP必选，最高优先级 |

**质量检查维度设计**：
1. **证据引用检查**(20分)：是否引用了至少1条reviewed evidence或confirmed Fact？引用的事实是否有sourceUrl？
2. **未确认事实检测**(20分)：扫描MOQ/交期/产能/认证/工厂数量/客户案例等关键词，是否标记了"待确认"？
3. **敏感信息扫描**(15分)：是否包含内部数据(成本/底价/利润率)？是否包含API Key/密码？
4. **垃圾邮件风险**(15分)：垃圾邮件关键词检测(免费/100%保证/限时/立即行动)、全大写比例、感叹号数量、链接数量
5. **CTA检查**(10分)：是否有明确的低摩擦CTA？CTA是否是yes/no问题？
6. **长度控制**(10分)：正文是否在60-150词最佳范围？主题行是否<60字符？
7. **个性化程度**(10分)：是否引用了客户具体信息(公司名/产品/市场/信号)？是否有通用模板痕迹？

### 候选6：线索去重和实体合并

| 评估项 | 内容 |
|--------|------|
| **用户问题** | 客户量增长后，同一公司可能被多次导入(不同来源/不同拼写)，导致重复开发、数据混乱、评分失真。当前仅CSV导入时有简单公司名+邮箱去重。 |
| **业务价值** | 🟠中高——数据质量基础，但当前客户量(39家)尚未触发严重问题。 |
| **使用流程** | 1.新增客户时自动检测潜在重复(域名/公司名规范化/邮箱域名) → 2.显示"可能重复"提示 → 3.人工确认合并 → 4.选择主记录→合并字段(联系人/证据/开发信/跟进记录迁移) → 5.被合并记录标记为merged |
| **输入数据** | 客户对象(company/website/email/country)、所有客户列表 |
| **输出数据** | duplicateCandidates[{customerId, matchType, matchScore, matchedFields}]、mergeResult{primaryId, mergedId, migratedRecords} |
| **所需接口** | 新增findDuplicates()(多维度匹配)、mergeCustomers()(数据迁移)、UI重复检测提示+合并确认页 |
| **是否需要模型** | ❌不需要——规则匹配(域名规范化/Levenshtein公司名相似度/邮箱域名) |
| **是否需要外部API** | ❌不需要 |
| **是否涉及客户隐私** | 🟡中——合并操作涉及客户数据迁移，需确保不丢失数据 |
| **开发成本** | 🟡中——约400-600行，匹配算法+合并逻辑+UI |
| **测试成本** | 🟡中——需测试各种重复场景和数据迁移完整性 |
| **维护成本** | 🟢低——匹配规则稳定 |
| **失败处理** | 合并前创建快照(可回滚)、合并失败不修改原数据、合并后被合并记录保留只读引用 |
| **推荐等级** | ⭐⭐⭐⭐ P2——MVP可选，客户量超过100后必需 |

## 三、推荐最终 MVP（4个功能 + 1个轻量附加）

### MVP 核心功能（3个，P1必选）

#### 🎯 MVP-1：开发信质量检查器（Draft Quality Checker）
- **优先级**：最高
- **核心理由**：工作台核心产出是开发信，当前AI草稿无自动质量门控。这是"证据驱动"理念的自然延伸，直接保护域名声誉和事实准确性。
- **开发量**：约500-700行
- **关键设计**：7维规则评分(证据引用/未确认事实/敏感信息/垃圾邮件风险/CTA/长度/个性化)，质量分≥70才能进入审核队列。

#### 🎯 MVP-2：线索质量和邮箱质量评分（Lead & Email Quality Scoring）
- **优先级**：高
- **核心理由**：在开发前过滤无效邮箱和低质量线索，聚焦高价值客户。MX记录用Node.js dns免费查询，无需付费API。
- **开发量**：约400-600行
- **关键设计**：邮箱质量(格式/企业域名/MX/域名匹配)+线索质量(网站/证据新鲜度/联系完整度/ICP)，D级客户标记"建议先补充资料"。

#### 🎯 MVP-3：客户开发任务队列增强（Task Queue with Retry）
- **优先级**：高
- **核心理由**：复用现有Campaign Task基础设施，增加失败重试/预计耗时/任务历史/逾期预警。解决单人外贸"跟进遗漏"最大痛点。
- **开发量**：约400-600行
- **关键设计**：扩展Campaign Task字段(failureReason/retryCount/estimatedMinutes/nextRetryAt)，3次重试上限，逾期标红，dailyWork页面增强。

### MVP 可选功能（1个，P2）

#### 🎯 MVP-4：线索去重和实体合并（Lead Dedup & Entity Merge）
- **优先级**：中高
- **核心理由**：数据质量基础，多维度匹配(域名/公司名相似度/邮箱域名)，人工确认合并，合并前快照可回滚。
- **开发量**：约400-600行
- **关键设计**：新增客户时自动检测潜在重复，合并时迁移联系人/证据/开发信/跟进记录，被合并记录保留只读引用。

### MVP 轻量附加（1个，低成本高价值）

#### ⚡ MVP-5：首次响应SLA计时（Inquiry Response SLA）
- **优先级**：中
- **核心理由**：研究显示35-50%单子给第一个响应者。实现极简单(新增firstResponseAt字段+计时+看板展示)。
- **开发量**：约100-200行
- **关键设计**：询盘创建时记录时间，首次回复时计算耗时，超4小时标红，dashboard显示平均响应时间。

## 四、MVP 总体评估

### 4.1 预计开发成本

| 功能 | 代码行数 | 预计工时 | 测试工时 |
|------|---------|---------|---------|
| MVP-1 开发信质量检查 | 500-700 | 6-8小时 | 2小时 |
| MVP-2 线索质量评分 | 400-600 | 4-6小时 | 2小时 |
| MVP-3 任务队列增强 | 400-600 | 4-6小时 | 2小时 |
| MVP-4 去重合并(可选) | 400-600 | 4-6小时 | 2小时 |
| MVP-5 SLA计时(附加) | 100-200 | 1-2小时 | 0.5小时 |
| **合计(核心3+附加1)** | **1400-2100** | **15-22小时** | **6.5小时** |
| **合计(全部5个)** | **1800-2700** | **19-28小时** | **8.5小时** |

### 4.2 技术可行性

- ✅ 全部基于现有数据结构(evidence/fact/customer/campaignTask)，无需新建数据模型
- ✅ 全部纯规则实现，不需要AI模型调用(不增加模型成本)
- ✅ 全部不需要外部付费API(MX记录用Node.js dns，网站检查用现有抓取)
- ✅ 全部不修改现有导航key，不破坏37功能
- ✅ 全部支持空状态/加载状态/错误状态/重复点击保护
- ✅ 全部不自动发送外部消息
- ✅ 全部事实来自知识库/证据/用户确认

### 4.3 风险和待确认事项

| 风险 | 等级 | 缓解措施 |
|------|------|---------|
| 开发信质量检查规则过严导致好草稿被误判 | 🟡中 | 质量门控设为"建议"而非"强制"，≥70分建议但不阻止，用户可手动跳过 |
| MX记录查询被目标域名DNS服务器限流 | 🟡中 | 查询超时5秒，批量查询时间隔1秒，失败标记"待确认" |
| 去重合并误操作导致数据丢失 | 🟡中 | 合并前创建快照，合并后被合并记录保留只读引用，支持撤销 |
| 任务队列重试导致重复AI调用 | 🟢低 | 重试仅针对任务状态推进，不重复调用AI(AI结果已缓存) |
| app.js体积进一步增大(当前2.3MB) | 🟡中 | 新功能优先写入独立JS文件(如draft-quality.js, lead-quality.js)，通过script标签引入 |

### 4.4 不建议加入MVP的功能及理由

1. **多联系人决策链**：数据模型变更影响面大，当前客户量(39家)尚未必需，留待第二阶段。
2. **购买信号监控**：需要定时任务框架和Tavily搜索配置，开发成本高，留待第二阶段。
3. **客户开发复盘增强**：当前数据量不足以产生统计显著结论，留待数据积累后。
4. **回复意图分类**：inbox已有AI总结，意图分类可作为第二阶段增强。
5. **客户关系图谱**：对单人业务价值有限，开发成本高。
6. **团队协作和权限**：OPC单人模式，非当前需求。
