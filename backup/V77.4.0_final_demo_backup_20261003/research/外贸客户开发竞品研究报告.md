## 一、执行摘要

### 1.1 研究结论

KaiLionCrafts 外贸获客 AI 工作台已建立**证据驱动的客户开发全链路**（找客户→核证据→写草稿→人工审核→跟进转化），在**事实安全边界**、**知识库深度集成**、**模型故障转移**三个维度领先于多数开源CRM。但在**开发信质量门控**、**邮箱/线索质量评分**、**任务执行保障**三个环节存在明显缺口，直接影响核心转化效率。

### 1.2 核心发现

| 维度 | 结论 |
|------|------|
| **工作台优势** | 证据→Fact→Pack→Campaign→开发信全链路可追溯；sanitizeFactsForAI三模式过滤；知识库588文档/9156切片深度集成；在线→本地模型故障转移 |
| **关键缺口** | 开发信无自动质量检查；邮箱无验证和质量评分；Campaign Task无失败重试；无多联系人决策链；无购买信号监控 |
| **开源可复用** | 仅2个项目(MIT/Apache)可直接复用代码：google-maps-scraper(MIT)、warmbly(Apache-2.0) |
| **开源可参考** | 11个项目可参考设计(UI/工作流/数据模型)，但代码不能拷入闭源产品 |
| **竞品最值得学** | Hunter.io邮箱置信度、Saleshandy多渠道序列、Attio Deal风险预警、ImportGenius贸易数据、Smartlead统一收件箱 |
| **推荐MVP** | 3个核心(P1)：开发信质量检查 + 线索/邮箱质量评分 + 任务队列增强；1个可选(P2)：去重合并；1个附加：首次响应SLA |

### 1.3 研究数据真实性声明

- GitHub项目数据：全部通过 GitHub REST API 实时拉取（2026-10-03），Star/Fork/License/pushed_at均为真实数据
- 商业产品数据：来自各产品官网公开页面，未编造功能、定价、用户数
- 视频/方法论：来自公开可访问的文章和框架文献，无法逐字核验的视频已标注 ⚠️ 待确认
- 工作台基线：来自实际代码读取（server.js/app.js/model-router.js等12个核心文件）

## 二、现有工作台基线

### 2.1 功能概况

- **37个功能页面**，全部通过测试，0失败
- **技术栈**：Node.js server.js(165KB) + 原生JS app.js(2.3MB) + index.html(62KB) + localStorage
- **AI模型**：智谱GLM在线优先 → Ollama本地兜底，5条模型链，慢响应检测，本地模型锁
- **知识库**：588 Markdown / 9156切片 / 16分类 / 三级权限(public/internal/confidential)
- **部署**：本地127.0.0.1:8080，Cloudflare Tunnel可选公网

### 2.2 客户开发五步闭环

```
找客户(autosearch/prospect/plans/devplans)
  → 核证据(website-evidence模块C深度分析/knowledgeFacts/knowledgePacks)
    → 写草稿(drafts/campaigns + AI生成 + sanitizeFactsForAI过滤)
      → 人工审核(reviewQueue/outreachQueue + 不自动发送)
        → 跟进转化(schedule/followUpPlan/inbox + 桌面通知)
```

### 2.3 核心竞争力

1. **证据驱动的事实安全**：website-evidence(SSRF防护+内容hash) → 人工核验 → createFactFromEvidence → Knowledge Fact → Knowledge Pack(版本冻结) → Campaign绑定 → 开发信引用。全链路可追溯。
2. **严格的AI输出边界**：sanitizeFactsForAI三模式(externalCompanyResearch/generalInternal/kaiLionOutbound)，confidential内容禁止发给任何AI，factEligible/templateEligible分层。
3. **可解释的客户评分**：prospect-priority.js 0-100分5维评分，6类硬性阻断，blocked客户无法生成公开草稿。
4. **完善的模型可靠性**：在线→本地故障转移，慢响应检测(>30s标记)，本地模型互斥锁，Trace脱敏记录。

### 2.4 关键限制

- app.js单文件2.3MB，维护成本高
- localStorage容量限制，无服务端数据库
- Tavily搜索未配置，自动搜客功能实际暂停
- 海关数据为演示数据
- 单联系人结构，不支持决策链
- 无定时任务框架

> 详细基线见：`research/现有工作台客户开发功能基线报告.md`

## 五、视频与方法论研究

### 5.1 核心方法论结论

| 方法论 | 外贸B2B适用性 | 建议用法 |
|--------|-------------|---------|
| **ANUM** | 高 | 冷联系时先找对人(Authority)，再确认需求(Need)、紧迫性(Urgency)、资金(Money) |
| **CHAMP** | 高 | 先谈痛点(Challenges)，再确认决策权、预算、优先级 |
| **Challenger Sale** | 高 | 给客户独特商业洞察，而非简单问需求 |
| **BANT-lite** | 中 | 询盘后资格认定，不全套照搬 |
| **MEDDIC-lite** | 中 | 重点客户用：Champion+量化痛点+决策流程 |
| **SPIN** | 中 | 首次电话/视频沟通时的提问框架 |
| **JTBD/Customer Development** | 中 | 产品开发和选品时用 |

### 5.2 外贸最佳实践

1. **海关数据工作流**：按HS编码搜索→筛选目标国家→分析采购频率和量→找到真实买家→背调→开发
2. **展会跟进SOP**：展前邀约→展中四要素记录(公司/需求/紧急度/下一步)→展后24h首封跟进→7天第二封→14天第三封
3. **开发信结构**：主题行(具体问题/结果)→开头一句完全关于收件人→价值主张(结果不描述产品)→低摩擦CTA(Worth a 15-min call?)
4. **多渠道Cadence**：Day1邮件→Day3邮件2(社会证明)→Day7 LinkedIn连接(无pitch)→Day12邮件3→Day16收尾
5. **首次响应SLA**：35-50%单子给第一个响应者，询盘后4小时内响应标绿，超24小时标红

### 5.3 购买信号体系

- **高价值信号**：融资公告、新高管上任(采购/进口经理)、供应商变更、新产品线发布、参展报名
- **中价值信号**：招聘激增(采购相关岗位)、官网改版、新市场扩张
- **低价值信号**：社交媒体活跃、博客更新

## 七、推荐最终 MVP

### 7.1 MVP 功能清单

| 序号 | 功能 | 优先级 | 开发量 | 核心理由 |
|------|------|--------|--------|---------|
| MVP-1 | **开发信质量检查器** | P1 | 500-700行 | 核心产出质量门控，证据驱动理念延伸，保护域名声誉 |
| MVP-2 | **线索质量和邮箱质量评分** | P1 | 400-600行 | 聚焦高价值客户，MX记录免费查询，无需付费API |
| MVP-3 | **客户开发任务队列增强** | P1 | 400-600行 | 复用Campaign Task，失败重试+逾期预警，解决跟进遗漏 |
| MVP-4 | **线索去重和实体合并**(可选) | P2 | 400-600行 | 数据质量基础，多维度匹配，人工确认合并 |
| MVP-5 | **首次响应SLA计时**(附加) | P2 | 100-200行 | 35-50%单子给第一个响应者，实现极简单 |

### 7.2 推荐理由

**为什么是这3个核心功能？**

1. **形成完整质量闭环**：线索质量评分(输入端过滤) → 开发信质量检查(产出端门控) → 任务队列增强(执行端保障)，覆盖客户开发全链路的质量控制。

2. **全部纯规则实现**：不需要AI模型调用(不增加模型成本)，不需要外部付费API(MX用Node.js dns，网站检查用现有抓取)，完全符合"不调用付费API"约束。

3. **全部复用现有数据**：开发信质量检查复用evidence/fact数据；线索评分复用prospect-priority评分框架；任务队列复用Campaign Task状态机。不新建数据模型，不破坏现有37功能。

4. **直接解决最高频痛点**：
   - 单人外贸最大问题是跟进遗漏 → 任务队列增强
   - 退信损害域名声誉 → 邮箱质量评分
   - AI草稿可能包含未确认事实 → 开发信质量检查

5. **开发成本可控**：核心3个功能约1400-2100行代码，15-22小时工时，可在一个开发周期内完成。

**为什么不选其他功能？**

- 多联系人决策链：数据模型变更影响面大，当前39家客户尚未必需 → 第二阶段
- 购买信号监控：需要定时任务框架和Tavily配置 → 第二阶段
- 客户开发复盘：当前数据量不足以产生统计显著结论 → 数据积累后
- 团队协作：OPC单人模式，非当前需求 → 不建议

### 7.3 预计开发成本

| 项目 | 核心3功能 | 全部5功能 |
|------|----------|----------|
| 代码行数 | 1,400-2,100 | 1,800-2,700 |
| 开发工时 | 15-22小时 | 19-28小时 |
| 测试工时 | 6.5小时 | 8.5小时 |
| 新增功能数 | 3 | 5 |
| 预计总功能数 | 40 | 42 |

### 7.4 实施顺序

```
MVP-5 SLA计时(最简单，1-2h)
  → MVP-1 开发信质量检查(最高价值，6-8h)
    → MVP-2 线索/邮箱质量评分(4-6h)
      → MVP-3 任务队列增强(4-6h)
        → MVP-4 去重合并(可选，4-6h)
```

每步完成后执行：node --check 所有JS文件 + git diff --check + 浏览器回归测试(原有37功能+新功能)。

### 8.1 技术风险

| 风险 | 等级 | 缓解措施 |
|------|------|---------|

| 任务重试导致重复AI调用 | 🟢低 | 重试仅推进任务状态，AI结果已缓存不重复调用 |

| 风险 | 等级 | 缓解措施 |
|------|------|---------|

1. **MVP范围确认**：Leo是否同意3个核心+1个可选+1个附加？还是只做核心3个？
2. **开发信质量门控强度**：≥70分是"建议"还是"强制阻止提交审核"？
3. **邮箱MX查询**：是否启用实时MX查询？(可能增加客户导入时间)
4. **去重合并**：当前39家客户是否已有重复？是否需要先做一次全量去重？
5. **Tavily搜索配置**：购买信号监控(第二阶段)需要Tavily API Key，是否配置？

### 8.4 不应该加入的功能

1. **客户关系图谱**：对单人业务价值有限，开发成本高
2. **团队协作和权限**：OPC单人模式，非当前需求，引入后大幅增加复杂度
3. **自动发送邮件/消息**：设计要求禁止自动发送，保持人工审核边界
4. **付费第三方数据集成**：成本高，单人业务ROI低
5. **全渠道自动化营销**：与"人工发送"设计原则冲突
