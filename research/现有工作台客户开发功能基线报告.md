## 四、客户评分和优先级逻辑

### 4.1 评分系统（prospect-priority.js，P2.3C-v1）

**0-100 分，A/B/C/blocked 四级分层，硬性阻断优先于分数。**

| 维度 | 分值 | 评分逻辑 |
|------|------|---------|
| ICP 匹配 | 0-30 | 产品匹配(0-12) + 市场匹配(0-10) + 买家类型匹配(0-8)，基于 Knowledge Pack 的 productScope/targetMarkets/buyerTypes |
| 身份和网站证据 | 0-20 | 身份已确认(0-8) + 有官网(0-4) + reviewed证据数量(0-8) |
| 产品和市场匹配 | 0-20 | 证据中目标市场(0-10) + 证据中买家类型(0-10) |
| 联系信息完整度 | 0-15 | 网站(0-3) + 联系人(0-4) + 邮箱/LinkedIn(0-5) + 国家(0-3) |
| 开发准备度 | 0-15 | approved Pack(0-5) + 无hard blocker(0-3) + 非DNC(0-2) + 无重复(0-2) + 有可用草稿(0-3) |

**分层规则**：
- ≥80分 → A级：优先人工开发
- 60-79分 → B级：补充资料后开发
- <60分 → C级：暂缓开发
- 有硬性阻断 → blocked：0分，不进入外联名单

### 4.2 硬性阻断（6类）

1. **DNC**：客户标记 dnc/doNotContact/status=dnc_blocked
2. **身份未确认**：identityStatus=unverified/pending
3. **重复未处理**：duplicateStatus=pending/confirmed
4. **Hard blockers**：客户对象上有未解决的 hardBlockers
5. **未绑定 approved Knowledge Pack**：context.pack.status≠approved 或无 pack
6. **明确拒绝联系**：rejectedOutreach/optOut

### 4.3 评分特点

- ✅ 可解释：每个维度有 positiveReasons 和 missingEvidence
- ✅ 证据驱动：reviewed 证据直接加分
- ✅ 安全边界：blocked 客户无法生成公开草稿
- ⚠️ 缺少：邮箱质量评分、公司基本面评分、购买信号评分、历史互动评分
- ⚠️ 缺少：评分历史趋势（无法看到客户评分随时间变化）

## 六、证据采集流程

### 6.1 网站证据采集（website-evidence.js，P2.5B）

**完整流程**：
1. URL 校验（SSRF防护：阻断 localhost/私有IP/内网域名/非http协议）
2. 网页抓取（连接超时10s/总超时30s/大小上限1MB/重定向上限5次/只解析text/html）
3. 内容提取（确定性提取：title/公司名/产品关键词/市场关键词/买家类型/联系方式脱敏）
4. 内容 hash（sha256前16位，用于变化检测）
5. 创建证据记录（默认 reviewStatus=pending, publicUseAllowed=false）
6. 人工核验（reviewWebsiteEvidence：pending→reviewed/rejected/conflict）
7. reviewed 证据可用于 ICP 评分和创建 Knowledge Fact

**多页采集**（P2.5B）：
- 支持 home/about/products/contact/custom 五种 pageType
- 单次最多3页
- 每页独立 evidenceId，页面级来源可追溯
- 去重：同 customerId 下已有 sourceUrl/finalUrl 匹配且无 error 的证据跳过

### 6.2 证据数据结构

```javascript
{
  evidenceId: String,
  customerId: String,
  sourceUrl: String,
  finalUrl: String,
  pageType: String,             // home/about/products/contact/custom
  pageTitle: String,
  fetchedAt: String,
  httpStatus: Number,
  contentHash: String,          // 可用于网站变化检测
  excerpt: String,              // 最多2000字符
  detectedCompanyName: String,
  detectedProducts: Array,
  detectedMarkets: Array,

  contactHints: Array,          // [{type, value}] 邮箱/电话已脱敏

  reviewedBy: String,

```

### 6.3 证据→Fact 流程（prospect-priority.js）

- `createFactFromEvidence()`：只有 reviewed + publicUseAllowed=true 的证据可创建 Fact
- 创建的 Fact 默认 reviewStatus=pending, publicUseAllowed=false, confidence=50
- Fact 需人工审核后才能 confirmed
- 高风险内容（认证/工厂/产能/MOQ）必须人工确认

### 6.4 限制

- ⚠️ 无定时重新采集（无法监控网站变化）
- ⚠️ contentHash 已计算但无变化对比逻辑
- ⚠️ 无招聘/融资/展会等购买信号采集
- ⚠️ 联系方式默认脱敏，无法直接用于外联（需人工补充）
- ⚠️ 无 LinkedIn 个人资料抓取

## 九、开发信草稿和人工审核流程

### 9.1 草稿状态流转

```
AI生成 → needs_review（待审核）→ reviewed（已修改）→ approved（已批准）→ sent（已发送，人工）
                ↓
            rejected（拒绝）
```

### 9.2 草稿生成约束

- `canGeneratePublicDraft()` 检查：
  - 优先级非 blocked
  - 至少有1条 confirmed + publicUseAllowed=true 的 Fact
  - 有邮箱或 LinkedIn
- AI 调用经过 `sanitizeFactsForAI()` 过滤（三种模式：externalCompanyResearch/generalInternal/kaiLionOutbound）
- 开发信 Prompt 包含 KaiLionCrafts Knowledge Base Context（factEligible 内容作为事实，templateEligible 仅作结构参考）
- 默认 online_safe 模式（GLM仅public知识库），local_only 可选

### 9.3 审核流程

- `reviewQueue`：集中审核所有待审核草稿
- `outreachQueue`：按优先级排序，逐个生成草稿
- 4封跟进序列内置
- A/B 测试（草稿级，非Campaign级）
- 效果分析和进箱率检测（基础）

### 9.4 限制

- ⚠️ 无开发信质量自动检查（证据引用/未确认事实/敏感信息/垃圾邮件风险/CTA/长度）
- ⚠️ 无 AI 生成审计记录的统一视图（model-trace 有记录但无前端展示）
- ⚠️ 无草稿版本对比
- ⚠️ 发送完全人工（工作台不自动发送，这是设计要求）

- ⚠️ 无跟进逾期率统计
- ⚠️ 无跟进节奏建议（基于客户类型和阶段的最佳间隔）
- ⚠️ 无回复意图自动分类（inbox有AI总结但无意图分类）
- ⚠️ 无多渠道触达序列编排

## 十一、知识库检索和引用机制

### 11.1 知识库规模

- 588 Markdown 文档，9156 切片
- 16个一级分类
- 三级权限：public(198) / internal(315) / confidential(75)
- authorityLevel=high：31篇
- factEligible：180篇
- templateEligible：422篇

### 11.2 检索架构（server.js retrieveKbContext）

```
前端请求 → GET /api/kb/context?q=...&purpose=...&provider=...
  → server.js retrieveKbContext(options)
    → purpose 校验（internal_ai/outbound/browse）
    → provider 校验（online_glm/local_ollama/none）
    → sensitivity 过滤（online_glm仅public，local_ollama public+internal，confidential禁止发给任何AI）
    → factEligible/templateEligible 分层
    → 返回 matchedFacts/matchedTemplates/citations/policySummary/excludedByEligibilityCount
```

### 11.3 Policy 规则

| 场景 | purpose | provider | 允许sensitivity |
|------|---------|----------|-----------------|
| 在线AI分析 | internal_ai | online_glm | 仅 public |
| 本地AI分析 | internal_ai | local_ollama | public + internal |
| 人工浏览 | browse | none | 按accessScope |
| 对外内容 | outbound | 任意 | 仅 public + confirmed，排除 pending/deprecated/conflictReview/noOutbound |

### 11.4 引用机制

- 开发信中关于 KaiLionCrafts 的事实只能来自 retrieveKbContext() → factEligible=true
- 知识库不可用时，注入安全提示："未找到已确认的公司知识库依据…必须标记为'待确认'，不得编造"
- 模块C深度分析中 External Evidence 与 KB Context 分离展示
- 客户画像中展示"公司知识库依据"可折叠区块

### 11.5 限制

- ⚠️ 向量检索暂未启用（当前为关键词检索）
- ⚠️ confidential 内容仅本机人工查看，无法被AI使用
- ⚠️ 知识库与客户开发知识库（outreachKB）是两套系统，未完全打通

## 十二、模型调用和故障转移机制

### 12.1 模型链（model-router.js）

| 任务类型 | 模型链 |
|---------|--------|
| 文本生成 | glm-4.7-flash → glm-4-flash → qwen3.5:9b → qwen2.5:7b |
| 推理 | glm-4.7-flash → qwen3.5:9b → deepseek-r1:7b |
| 视觉 | glm-4.6v-flash → qwen3.5:9b → qwen2.5vl:7b |
| 生图 | cogview-3-flash → x/flux2-klein:4b-fp4 |
| Embedding | nomic-embed-text:latest（固定） |

### 12.2 故障转移规则

**允许转移**：408/429/5xx/timeout/abort/connection_refused/network_error/slow_response/rate_limited/service_unavailable/not_configured/empty_response/parse_error

**禁止转移**：400/401/403/422/content_moderation/invalid_api_key/invalid_parameter（配置错误需人工处理）

### 12.3 慢响应检测

- 单次>30秒 → 标记慢模型
- 连续两次>15秒 → 标记慢模型
- 慢模型5分钟过期，自动模式下跳过慢模型直接尝试下一个

### 12.4 本地模型锁（local-model-lock.js）

- 进程级互斥锁，所有本地大模型共用一把锁
- 同时只允许一个本地大模型执行
- 等待队列和超时处理（等待60s，持有120s）
- embedding 模型不参与锁
- 成功/失败/超时/取消均释放锁

### 12.5 Trace 记录（model-trace.js）

- 内存存储，最多500条，不写入文件
- 记录：模型、任务类型、成功/失败、延迟、故障转移详情
- 脱敏：apiKey/password/token/secret/cookie/thinking 等字段自动 [REDACTED]
- 不记录完整 Prompt 和敏感客户信息

### 12.6 限制

- ⚠️ 无模型调用成本统计（token usage 未持久化）
- ⚠️ 无按功能维度的模型调用分析
- ⚠️ 异步任务（generate-async）有 job 管理但前端展示有限

## 十五、当前已知限制

### 15.1 技术限制

1. **app.js 体积过大**（2.3MB）：单文件前端，维护成本高，加载时间长
2. **localStorage 容量限制**：浏览器通常5-10MB，客户数据量大时可能溢出
3. **无服务端数据库**：所有业务数据在浏览器 localStorage，换设备/清缓存即丢失
4. **向量检索未启用**：知识库当前为关键词检索，语义匹配能力有限
5. **CSP 策略已移除**：因触发广告拦截扩展，XSS防护依赖代码层 esc()
6. **AI 输出未 sanitize**：建议引入 DOMPurify
7. **表格横向滚动**：部分表格缺少 .table-wrap 包装

### 15.2 安全限制

1. **Git 历史存在旧 API Key**：Leo 已知悉并接受，公网部署前需轮换和清理
2. **Cloudflare Access 未配置**：公网受控展示暂不可上线
3. **localStorage 含真实客户数据**：公网展示前需切换演示数据
4. **默认绑定 127.0.0.1**：局域网无法直接访问（设计正确）

### 15.3 业务限制

1. **Tavily 搜索未配置**：自动搜客功能实际暂停
2. **海关数据为演示数据**：非真实贸易数据
3. **无真实邮箱验证**：无法检测邮箱有效性
4. **单联系人模型**：不支持决策链管理
5. **无定时任务**：无法自动重采证据、监控变化、发送提醒
6. **模块D（痛点识别）未开发**：交接文档中规划为 V77.5

### 15.4 已知非阻断问题

- `migrateData is not defined` 控制台错误（历史遗留，不影响功能）
- 三家公司完整端到端回归未执行（按"不产生真实模型调用"限制保留）

## 十六、基线总结

### 工作台核心优势

1. **证据驱动的客户开发流程**：网站证据采集→人工核验→Fact→Pack→Campaign→草稿，全链路可追溯
2. **严格的事实安全边界**：sanitizeFactsForAI 三模式 + 知识库三级权限 + fact/template分层
3. **完善的模型故障转移**：在线优先→本地兜底，慢响应检测，本地锁，Trace脱敏
4. **人工审核边界清晰**：不自动发送，所有AI输出需人工确认，DNC/blocked硬性阻断
5. **知识库深度集成**：588文档/9156切片，开发信和深度分析均引用知识库事实

### 最关键的3个缺失

1. **开发信质量自动检查**：当前AI草稿生成后无自动质量门控，完全依赖人工审核发现问题
2. **邮箱质量和线索质量评分**：无法在开发前过滤无效邮箱和低质量线索，浪费开发精力
3. **多联系人决策链**：B2B采购涉及多决策人，单联系人结构无法管理复杂客户关系
